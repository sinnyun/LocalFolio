# 画板只存本地文件链接，并按缩放比例生成分层 LOD 代理

画板要把大量本地图片放上无限画布。把图片字节（base64 或 blob）写进画板快照是最省事的做法，但快照会随图片线性膨胀：几十张大图之后，保存、加载、撤销栈和多人协作的每一条路径都在搬运几十上百 MB 的 JSON。另一个问题是渲染：一张 8000 万像素的原图在缩放后仍然整张解码进显存，画布一卡就是因为这个。

因此两件事一起钉死：

1. **画板 JSON 只记录本地文件路径与原始像素尺寸等元信息**，绝不写入 base64 图像数据。图片的字节永远留在文件系统上，画板只持有指针。浏览器拖入或粘贴拿不到磁盘路径时，Host 以 1 MB 分片（`IMPORT_CHUNK_BYTES`，单图上限 128 MB）接收字节，写入插件托管目录 `plugins/workspace-canvas-host/data/imports/`，再以普通本地文件链接加入画板——拖入的图片最终和本地图片是同一种东西，不引入第二种图片身份。
2. **渲染走分层 LOD 代理**：界面按画布缩放（`steppedScreenScale`）与屏幕 DPR 请求 `256 / 512 / 1024 / 2048` 四档代理图之一，Host 用 Windows WIC 的 `DecodePixelWidth` 按目标尺寸直接解码（不先解全图再缩放），必要时回退到 Shell 缩略图，结果落盘 LRU 缓存。缓存放在 `cache/lod/`，上限 256 MB / 1500 个文件，删掉只是下次重新生成。

## Consequences

- 画板文档体积与图片数量脱钩，保存和加载开销只看画板元素数量。
- 路径会失效：图片被移走或重命名之后，画板里只剩一条断链。这是纯链接方案必然付出的成本，对策是显式的——画板列表带断链角标，状态胶囊里的小面板支持单张重选与按文件夹批量重定位。
- `cache/` 与 `data/` 的边界因此变得重要：`cache/lod/` 可随时清空，`data/imports/` 是用户数据的真源，绝不能当缓存清。
- 原图永远不被改写。LOD 只产生新的代理文件，回退到原图时看到的就是用户原本那张图。
- 违反信号：画板 JSON 里出现 base64 字段，或界面直接 `<img src>` 原图路径而不带 tier 参数。
