# 物料以 `.vectorcraft` 文件为唯一真源，经 CLI 与前台控制通道读写

物料工作区整理的是 A3 横版（420×297mm）的 `.vectorcraft` 文件。这些文件同时被本地 VectorCraft 程序使用，用户会两边来回切：在工作台里改标题、材质、工艺，切到 VectorCraft 里再改一遍，然后又切回来。

如果工作台把物料信息复制进自己的数据库再单向往外写，两边就会分叉，而且是用户看不见的分叉——他改的是同一个东西的两份副本。因此定下：

1. **文件是唯一真源。** 页面顺序、页码、物料信息头都以 `.vectorcraft` 文件里的实际内容为准，工作台不持有可独立编辑的第二份真值。
2. **两条通道，各有分工。** 后台写走 `vectorcraft-cli`（默认查找 `C:\Program Files\VectorCraft\vectorcraft-cli.exe` 与其 x86 路径，可在设置里覆盖）；前台已在运行时走 `vectorcraft --control` 的本地控制端口（默认 `7979`）。两条通道都由 Host 侧持有，界面只发意图。
3. **外部改动回流靠 watcher。** 用户在 VectorCraft 里改了文件，Host 的文件监听把变更推给界面刷新，而不是等用户手动点「重新加载」。设置里可关掉自动监听（`autoWatchFiles` / `autoPollLiveControl`）。
4. **导出用程序自己的导出能力。** 单图（PNG/JPG/WebP/SVG）与多页 PDF 交给 CLI 原生导出，不在工作台里重画一遍 PDF 生成器。

真正属于工作台自己的数据只有补充层：`projects.json`（项目与关联文件）、`catalog.json`（默认/项目物料数据）、`page-meta.json`（逐页信息头缓存）、`settings.json`（CLI 路径、控制端口、监听开关）。这些是**索引与默认值**，不是文件的替代品。

## Consequences

- 读之前要能容忍文件被外部修改甚至删除：解析失败和缺失都走显式的错误/空态，而不是崩溃或静默覆盖。
- 写入必须可诊断：找不到 CLI 时提示具体路径与「请在设置中配置」，而不是一个笼统的失败。
- 双向同步不许做「最后写入者获胜」的静默合并——以文件为准，并把可能被覆盖的字段在界面上标出来。
- 无 VectorCraft 的机器上，工作区可以浏览已有关联但无法导出与写回；这是设计允许的半可用状态，不是要补的漏洞。
- 违反信号：出现一个「工作台自己的页面顺序」字段，或导出不经过 CLI 而自绘 PDF。
